# Architecture & Tech Stack

General product concept lives in `idea.md`.

## Tech Stack

### Frontend (No React)
- **Framework**: **Svelte 5** (using Runes: `$state`, `$derived`, `$effect`) with **SvelteKit** and **TypeScript**.
  - Fine-grained reactivity updates individual DOM nodes (ideal for high-frequency multiplayer board and corner-note updates) without Virtual DOM overhead.
  - Built-in `svelte/motion` (`Spring`, `Tween`) and `svelte/transition` primitives for nuanced micro-animations.
- **SEO & game hubs**: Shared catalog in `frontend/src/lib/games/catalog.ts` plus scribbly `GameLogo.svelte` icons. The landing page lists games in catalog order and, after load, re-sorts them by `play_count` from `GET /api/games` (number of non-lobby rooms per game still in the DB, i.e. roughly games started in the last year). Each game has a prerendered hub at `/{slug}` (`GameHub.svelte`: description, create room, open sessions for that game). Landing and hubs emit per-page title/description/canonical/OG/JSON-LD via `SeoHead.svelte`. `static/robots.txt` + `static/sitemap.xml` list those URLs. Room play stays at `/{slug}/{roomId}` via adapter-static `200.html` SPA fallback. FastAPI serves prerendered `{slug}.html` (or `{slug}/index.html`) for hubs and falls back to `200.html` for room routes.
- **Styling & Scribbly Visuals**:
  - **Tailwind CSS v4** + native CSS custom properties.
  - **Fonts are self-hosted** via `@fontsource/*` packages imported in `+layout.svelte` (bundled by Vite). No third-party requests (no Google Fonts, CDNs, analytics); keep it that way.
  - **Rough.js** + inline **SVG** with `stroke-dasharray`/`stroke-dashoffset` animations and subtle SVG displacement filters (`#scribble-filter`) for a minimalistic, hand-drawn scribbly look.
- **Color System (`opponent_color`)**:
  - **OKLCH perceptual color space** in `frontend/src/lib/core/color.ts` for `opponent_color(my_color, their_color)`.
  - Keeps other players' colors unchanged unless they are perceptually too similar to `my_color`, in which case it deterministically assigns a distinct color from `PRESET_PLAYER_COLORS`.
- **Build & Package Manager**: **Vite 8** + **pnpm 12** (Node 26 in Docker); production uses `@sveltejs/adapter-static` (SPA fallback) so FastAPI can serve the built site.
  - **SvelteKit 3**: there is no `svelte.config.js`; adapter and preprocess options are passed to `sveltekit({...})` in `frontend/vite.config.ts`. `tsconfig.json` extends `$app/tsconfig`.
  - Shared code is imported via the `#lib/*` subpath import (`package.json` `imports`, replaces `$lib`). Write imports with explicit extensions (`#lib/core/auth.svelte.ts`, `#lib/games/catalog.ts`); extensionless `#lib` paths do not type-check.
  - TypeScript stays on 6.x until `svelte-check`/SvelteKit accept 7.

### Backend
- **Language & Packaging**: **Python 3.13+** managed with **uv**.
- **Web & Realtime Framework**: **FastAPI** + **Uvicorn** (with native `WebSockets` and `asyncio`).
- **Validation & Protocol**: **Pydantic v2** discriminated unions for typed client/server WebSocket messages and REST endpoints.
- **Database**: **PostgreSQL 17** accessed directly via **Psycopg 3** (`psycopg[binary,pool]` with `AsyncConnectionPool`), configured via `docker-compose.yml` (`postgresql://games:games@localhost:5434/games` by default, overrideable with `DATABASE_URL`).
  - Shared relational tables (`rooms`, `room_players`, `player_stats`, plus `users`, `auth_sessions`, `auth_email_tokens`, `oauth_accounts`) and `JSONB` for game-specific board state so games can be resumed and share room infrastructure without rigid schema coupling.

## Accounts (optional)

Playing stays anonymous by default (random `player_id` in `localStorage`). Accounts are additive: `users.player_id` is the stable id, so stats and recent rooms follow the account. Sign-up adopts the browser's current anonymous id unless taken; after login the frontend (`auth.svelte.ts`) switches `profile.playerId` to the account's id and generates a fresh anonymous id on sign-out.

- Backend (`core/auth.py`, `auth_api.py`, `oauth.py`, `mail.py`, routes under `/api/auth`): email + password (argon2), Google OpenID Connect (authorization code + PKCE, hand-written with `httpx`; a signed `games_oauth` cookie binds the flow to the browser), email verification and password reset via single-use hashed tokens. Sessions are opaque random tokens stored hashed in `auth_sessions` (HttpOnly, SameSite=Lax cookie `games_session`, 30 days sliding, `Secure` when `PUBLIC_BASE_URL` is https) — no JWTs. Password change/reset revokes all sessions. Rate limits are in memory and keyed by email, never by IP. If Google signs in to an address that was registered but never verified, the unverified password is dropped (prevents pre-registration takeover). Deleting an account removes its stats, push subscriptions and hosted rooms.
- CORS is limited to `PUBLIC_BASE_URL` and `http://localhost:5173` because cookies carry login state.
- Frontend routes: `/login` (sign in / sign up / forgot), `/account`, `/verify-email`, `/reset-password` (SPA fallback, `noindex`).
- Name and ink colour live on the account (`users.display_name`, `users.color`, `POST /api/auth/account/profile`). Signed-in users edit them on `/account`; the landing page and game hubs hide the profile box for them. Changes from the in-room badge are saved to the account too (debounced in `auth.saveProfile`). On first sign-in without a stored colour, the current local colour is adopted.
- Mail goes out via the SMTP server of Linevast (domain registrar and email provider; named in the privacy page). Config via env, see `.env.example` (`PUBLIC_BASE_URL`, `AUTH_MAIL_BACKEND`, `SMTP_*`, `GOOGLE_CLIENT_*`). Not implemented: change email, Apple sign-in.
- Friends (`core/friends.py`, routes under `/api/friends`, all require the session cookie): mutual friendships between accounts in `friendships` (one row per direction) and `friend_requests` (`declined_at` set on decline; a declined request still looks pending to the sender and blocks a new one until requests expire after 30 days). Requests can only be sent to a co-player with an account in a room you are both in (`GET /api/friends/rooms/{room_id}` returns `none`/`outgoing`/`incoming`/`friend` per co-player with an account, so accounts are only revealed to people you play with); adding someone who already asked you accepts their request. Either side removes silently. `GET /api/friends` returns friends with a `label` (duplicate names numbered by when they were added, `friend_labels`), incoming and outgoing requests; users are referenced by `users.id`, never by email or player id. Nothing exposes online state or last activity. Frontend: `friends.svelte.ts` store; `RoomShell` loads the room statuses, and clicking a co-player's name in `PlayerBar`/`Lobby` opens `PlayerActionsModal` (add friend, and for the host remove from room); `/account` lists requests and friends.
- Invites and friends' lobbies (`core/friends.py`): `room_invites` (one per room and friend, `ON DELETE CASCADE` with the room, dropped when the friendship ends; `mailed_at` for the invite-mail limit). `POST /api/friends/invites` (sender must be in the room, only friends not already there, 30 per sender per day) sends a push via `WebPushService.send_to_player` (`format_invite_notification`) and, if opted in, a mail; both run as background tasks (`FriendService.flush` for tests). `GET /api/friends/rooms/{room_id}` also returns `invited` and `friends_here`; `GET /api/friends/inbox` lists invites to unfinished rooms you haven't joined; `GET /api/friends/lobbies` lists rooms hosted by friends in `lobby` status (no timestamps, sorted by game and host). Frontend: invite button in the `RoomShell` header (signed-in) opens `InviteFriendsModal`; `/friends` shows invites and lobbies; the landing page has a Friends button with the invite count.
- Notification mails (`core/notify_mail.py`, `NotificationMailer`): opt-in `users.notify_mail_turn` / `notify_mail_invite` (`POST /api/auth/account/notifications`, exposed as `mail_turn`/`mail_invite`), only for verified addresses. `RoomManager._schedule_turn_push` also calls `mailer.queue_turn` (upsert into `turn_mail_queue` with `due_at = now + 15 min`, only for opted-in accounts); a 60 s loop in `main.py` claims due rows (`DELETE … RETURNING`) and mails only if the room still plays, `state.current_player_id` is still that player and they aren't connected. Invite mails: at most one per inviter and recipient per 24 h. Every mail carries an HMAC unsubscribe token (`AuthService.unsubscribe_token`, signed with the auth secret): `/unsubscribe?token=` page with a button (so link scanners don't trigger it) and `List-Unsubscribe` one-click to `POST /api/mail/unsubscribe`. `send_email` takes optional extra headers.

## Modular Structure & Standalone Extractability

To share components across games while allowing any game to be extracted and run standalone:

1. **Core Layer (`core`)**:
   - **Backend (`backend/games_platform/core/`)**:
     - `db.py`: Psycopg 3 `AsyncConnectionPool`, schema initialization (`rooms`, `room_players`, `player_stats`, `app_settings`, `push_subscriptions`), and expired room cleanup (2 days without moves, 1 year with moves) plus `player_stats` untouched for 1 year. `player_stats` keeps per game: completed games, wins, total score, overall best and the best split into `best_score_single` (room had exactly one player) and `best_score_multi` (2+ players, bots count); the split columns were backfilled once from the finished rooms still stored, so older results whose rooms were already deleted stay `NULL` (shown as –). The "Server stats" (rounds played, points scored) are running totals in `app_settings` key `server_totals`, incremented in `record_game_finished` and seeded once from the stored data, so deleting rooms or stats never lowers them. The app container runs uvicorn with `--no-access-log` (no IPs logged by the app; data retention is described in the privacy page `frontend/src/routes/privacy/+page.svelte`).
     - `protocol.py`: `GameDefinition` protocol and Pydantic v2 discriminated unions for WebSocket/REST messages.
     - `push.py`: `WebPushService` for auto-generated/persisted VAPID keys and asynchronous `pywebpush` turn-notification delivery. Subscriptions are per player and device, not per room: `push_subscriptions` has one row per endpoint (unique), owned by the player currently using that browser, so subscribing again under another id (sign in/out) moves the device; turn pushes go to all of the target player's devices. API: `POST/DELETE /api/notifications/subscribe` (DELETE needs the endpoint), `GET /api/notifications/status`; an optional `room_id` on subscribe counts as activity in that room. Rows untouched for a year are cleaned up (every page load with notifications on refreshes them). The old per-room rows were merged once on schema init (one per endpoint, most recent player). Endpoints are limited to known push-service hosts (at most 5 per player). Pushes use a 5-minute TTL and a per-room Topic so a later turn replaces a queued alert. Set `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` when more than one process serves the app.
     - `protocol.py` optional game hooks (looked up with `getattr`): `on_game_ended(state, config)` adjusts state when the host ends a game early (North South Sort reveals its discarded cards); `get_player_view(state, config, viewer_id)` makes `RoomManager` send each connection its own `room_state` (hidden information such as a secret word; REST snapshots use `viewer_id=None`), and `on_player_removed(state, config, player_id)` runs after the shared `turn_order` fix-up when someone leaves mid-game. Mid-game joiners are appended to `turn_order` (`RoomManager._add_midgame_player`); if the game was being played alone, the solo player has already moved (`move_count > 0`; before that the opener keeps the turn) and the game sets `solo_turn_goes_to_joiner = True` (Silbenstreit, Spellsprawl, Käsekästchen, North South Sort, Fragmentory; not Emoji Charades, whose explainer rotates per round), the joiner gets the turn right away. `on_player_joined(state, config, player_id)` then fixes up game state (North South Sort deals the hand and restarts the turn clock, Fragmentory deals the card).
     - Bot players (hooks `get_bot_players(config)` and async `bot_turn(room_id, state, config, bot_id)`): bots have ids prefixed `ai:` (`is_bot_id`), get a ready `room_players` row (score, player bar, `is_bot` in snapshots, always shown as connected) that `RoomManager` syncs on room create, config update and game start. They are never in `turn_order`, cannot be removed by the host or claimed by a client, and are skipped in `player_stats`. After each human game action `RoomManager` restarts a per-room `BOT_DEBOUNCE_SECONDS` (3 s) timer; when it runs out, `bot_turn` runs without the room lock (it may call an LLM) and a returned action is applied like a player action, unless the optional hook `bot_action_is_stale(state_before, state_now)` says a human changed the relevant state meanwhile (Emoji Charades: the clues), in which case it is dropped and the restarted timer gives the bot a fresh turn. Only one bot run per room at a time; changes during a run trigger one more run afterwards.
     - Full rooms (optional game hook `max_players(config)`, read via `seat_limit` / `is_room_full` in `protocol.py`; bots don't take seats): a room whose human seats are all taken cannot be joined; players already in it can always come back. The snapshot carries `max_players` (null = no limit). The WebSocket endpoint closes newcomers with code `4005`. Like `4004` (room not found) and `4003` (reserved id) it accepts before closing, since a close before `accept()` reaches browsers as `1006`, which the client treats as a network drop and keeps reconnecting. `player_sync` to a new id is refused when full, the host cannot change settings so the limit drops below the players present, friends' lobbies skip full rooms (unless you are in them; `FriendService(seat_limit=...)`) and invites to them are refused; `RoomShell` hides the invite button. Silbenstreit: 4 seats, 1 in solo mode. Sudoku Zero: 2 seats, 1 in solo mode.
     - `llm.py`: Minimal async OpenRouter chat client (`OPENROUTER_API_KEY`, `OPENROUTER_MODEL`, default `deepseek/deepseek-v4.1-flash`; reasoning off, `provider.data_collection=deny`), same setup as eventmat.
     - `room_manager.py`: WebSocket room/lobby lifecycle (a finished game's host-only "New Round" button sends `return_to_lobby`, so every player lands in the lobby where the settings can be changed), host-only `end_game` message (playing → finished with final scores, usable by any game), starting player (on `start_game` the join order is rotated so `turn_order[0]` opens: a random player in a room's first game, afterwards the loser of the previous game, i.e. the lowest-scoring human, random among ties, stored in `rooms.next_starter_id` by `record_game_finished`; random again if that player left; Emoji Charades ignores this and shuffles the explainer order every game), non-creator player leave handling (including automatic leave when a new player joins a running game and disconnects without acting) and host player removal (creators cannot leave a room, only delete it or remove other players), 10-second streak multiplier tracking (`1.1x` starting after first right entry), turn-change Web Push dispatch, and PostgreSQL state persistence.
   - **Frontend (`frontend/src/lib/core/`)**:
     - `profile.svelte.ts`: Player profile store (`localStorage` UUID, name configuration tracking, and primary color).
     - `color.ts`: Perceptual OKLCH similarity check and preset-palette `opponent_color(my_color, their_color)` resolver.
     - `ws.svelte.ts`: Auto-reconnecting typed WebSocket client.
     - `notifications.svelte.ts` + `static/sw.js`: Opt-in turn notifications combining the client `Notification` API, tab title `🔔` indicator, and Service Worker Web Push subscriptions. One switch per device (`pushNotifications` store, localStorage `games_push_notifications_v2`; the old per-room map turns it on if any room had it), toggled by the bell in any game (`TurnNotificationBell`) or on `/account`. The root layout re-registers the device whenever `profile.playerId` changes, after the auth state has loaded.
     - `components/`: `ScribblyBox.svelte`, `ScribblyButton.svelte`, `ProfileBadge.svelte`, `NamePromptModal.svelte`, `PlayerActionsModal.svelte`, `PlayerBar.svelte` (optional `previewScores` shows the scores a pending move would give, in italics; Spellsprawl and Silbenstreit compute them client-side while a word is being composed), `TurnNotificationBell.svelte`, `RoomShell.svelte`, shared `Lobby.svelte`, and `ZoomBoard.svelte` (board canvas shared by Spellsprawl and Fragmentory: hidden scrollbars, one-finger/wheel scrolling, two-finger pinch and Ctrl/⌘+wheel zoom anchored at the fingers/pointer in grid coordinates (`originX/Y` = the grid cell at the content's top-left, which moves while the padding adapts), +/− buttons, and a height from its top to the window bottom minus `reserveBelow` (the panel below it incl. the gap, measured with `offsetHeight`), its own border and the bottom padding/borders of its ancestors, at least `minHeight`, so the page does not scroll).

   - **Backend (`backend/games_platform/games/north_south_sort/`)** (slug `north-south-sort`):
     - `game.py`: `NorthSouthSortGame` (1–8 players, round-based via `turn_order`). Config: `language` (de/en names), `continent` (`world` or one continent; Antarctica only in `world`), `difficulty` (`easy` / `medium` / `hard`, default medium: each `(continent, category)` pool is ranked by `difficulty_score` = fame + 2·log10(sitelinks), and the bands are cumulative — easy = best-known third, medium = two thirds, hard = all; states without the key draw from the full pool), `categories` subset, `timed`, `end_condition` `rounds` / `points` / `failed_round` (a round where everyone skipped or misplaced). State keeps location ids only: `axis` (south→north, starts with a random city), public `hands` (one card per selected category, refilled from the filtered pool minus `used_ids`), hidden `discarded`. `place` is correct when the card's lat box overlaps the gap between its neighbours (`is_correct_slot`); right = base × category value (1/2/3) × speed factor (×2 within 10 s, ×1.5 within 20 s when timed, server clock `turn_started_at`), where base = 10 ÷ gap between the neighbours' latitudes (to the pole at either end), rounded half up and clamped to 1–20 (`base_score`, mirrored in the client's slot preview); wrong = −category value and the card is discarded unrevealed. `skip` swaps the whole hand (old cards go back into the pool). `get_public_view` resolves ids to card data; hand cards carry no lat/description, `discarded` only appears once `finished`. `draw_hand` deals mid-game joiners a hand. Ignores the platform streak multiplier.

     - `locations.py`: `Location` dataclass (en/de name, center, approximate min/max lat/lon with `bounds_source`, en/de description, Wikipedia links, country, one `continent`, `fame` 1–5, sitelinks), `CATEGORY_POINTS` (`city` 1, `landmark` 2, `event` 3) and `load_locations()`.
     - `locations.json`: committed dataset (~1000 per category), regenerated with `make locations`.
     - `generate_locations.py`: offline generator. Wikidata SPARQL in two phases (cheap per-class candidate lists ranked by sitelinks, then detail lookups in batches of 100 QIDs, failing batches split in halves; combined continent filters time out on WDQS). Events without own coordinates use `P276`/`P1071` location (dropped if that place is > 50,000 km²). Bounds come from extreme points (`P1332`–`P1335`), else area as a square, else a per-category default radius; boxes over 10° fall back to the default. Transcontinental countries are split by simple coordinate rules (`pick_continent`). Shortlist (1.5× target, per-continent floor, widened while too few survive) goes through an OpenRouter curation pass (`keep`, `fame`, one-sentence en/de descriptions without direction hints) via `core/llm.py`; `--no-llm` uses Wikidata descriptions and sitelink-based fame. Wikidata responses and LLM answers are cached in `backend/.cache/north_south_sort/` (gitignored).

   - **Frontend (`frontend/src/lib/games/north-south-sort/`)**:
     - `NorthSouthSortGame.svelte`: Vertical axis (north on top) with "place here" slots between cards once a hand card is selected, sticky bottom hand bar with Skip and the timed ×2/×1.5 countdown, other players' hands, last-move line, host "End game". Misplaced cards appear in red at the attempted slot, shake and drop away.
     - `FinalMap.svelte`: End-of-game map replacing the axis: Natural Earth 110m land outline (`world-atlas`, unpacked with `topojson-client`, drawn with `d3-geo`'s equirectangular projection so north–south stays vertical), lazy-loaded as its own chunk and bundled (no third-party requests). Framed to the played locations; placed cards are dots in the player's colour, misplaced ones red ✕; hover/tap/focus a point to show its card below the map.

   - **Backend (`backend/games_platform/games/fragmentory/`)**:
     - `board.py`: Pure board logic. Each card side is split into two half-edges (8 per card, clockwise from the top-left); a card type is its line sides plus its areas as half-edge sets (`straight`, `curve`, `cross`, `t`, `end`, `blank`; rotation = `+2` per quarter turn). Areas of neighbouring cards sharing a half-edge form regions (union-find, `compute_regions`). A region's colour is derived from its areas' `owners`: none (white), one player, or several (gray tie). `place_card` checks line/no-line matching and that a claim is allowed (`claim_allowed`: no area of the card touches a region holding any of the player's cards (`grows_own_area`), and the claimed area touches no other player's region; white and gray are fine), then resolves every region touching the new card: one owner → all its areas take that colour; several owners → the one with the most cards wins if it leads by 1 (fresh merge) or by 2 (the region already contained a gray tie), else it stays gray. `territory_scores`: cards per single-colour region, 0 for one-card regions, ×2 when no half-edge faces an empty cell (enclosed).
     - `game.py`: `FragmentoryGame` (1–8 players, no config, round-based via `turn_order`). The extra start T sits at `0,0`; the 42-card deck (6 straight, 12 curve, 6 cross, 10 T, 4 end, 4 blank) is hidden in the public view (`deck_counts`, `deck_size` instead); every player holds one public card (`hands`). Claiming an area is optional; `discard` is only accepted when the card fits nowhere. Scores are recomputed every move as `territory − penalties` (penalty = growth of the bounding-box area for the player who grew it) and sent as deltas (`points_delta` + `extra_score_deltas`). Mid-game joiners are dealt a card on the next move; the game ends when deck and hands are empty.
     - `standalone.py`: Standalone FastAPI entrypoint.
   - **Frontend (`frontend/src/lib/games/fragmentory/`)**:
     - `board.ts`: Client mirror of `board.py` (regions, legal spots, claims, placement preview, scoring) plus the card shapes for drawing.
     - `FragmentoryGame.svelte`: SVG board in a `ZoomBoard` (cards + a two-cell margin, padded to fill the canvas, which leaves room for the card panel right below it — the panel holds the card, Rotate/Place, the host's End game button and the other players' cards; follows each new card; dashed used-area frame), tap a spot, then tap the card (on the board or in the bar) or ↻ to rotate through the fitting rotations (visually identical ones, `shapeKey`, are skipped), then tap one of the empty circles (card panel or board) marking the areas that may be occupied; the pending move is previewed on the board and in the player bar (italics). Each player's latest card has a thin frame in their colour. Region shading: pale = one card, solid = open, dark = enclosed, gray = tie. Deck and Rules overlays (the rules snippet is also the lobby text) instead of always-visible rules.
     - `CardIcon.svelte`: Small line-only card icon.

   - **Backend (`backend/games_platform/games/sudoku_zero/`)** (slug `sudoku-zero`):
     - `scoring.py`: Solution counts capped at 1000 (`cap`), `placement_points` (+1 only while the count is still 1000+, plus `round(100·log2(min(before,1000)/after)·min(1,(17/clues)²))` with clues counted after placing — the weight keeps the bonuses from always summing to ≈ 997), `end_bonus` (`round(1000·clamp((80−clues)/63,0,1)²)`), `has_conflict`, and a bitmask MRV `count_solutions(grid, limit)`.
     - `game.py`: `SudokuZeroGame` (config `solo`; `max_players` 1 or 2; round-based via `turn_order`; own scoring, ignores the streak multiplier). Starts from an empty grid; `place` carries the client's capped solution count. **Trust model**: counting is done by the client to keep server load low; the server checks the Sudoku rules itself, rejects counts that grow, and verifies a claimed `1` (unique) with `count_solutions(limit=2)`; `0` and `2..1000` are trusted (lying only hurts the liar or makes the board unwinnable). Unique → game ends with the end bonus (multiplayer: split evenly, other half via `extra_score_deltas`). A 0-solution clue costs 50: solo ends the game (`failed_cell`, shown red, not part of the grid), multiplayer rejects it and passes the turn. Solo `give_up` ends the game keeping the score; multiplayer ends on two consecutive passes or two consecutive 0-solution clues. `end_reason` says why.
     - `standalone.py`: Standalone FastAPI entrypoint.
   - **Frontend (`frontend/src/lib/games/sudoku-zero/`)**:
     - `solver.ts`: Client mirror of the scoring formulas (`placementPoints`, `endBonus`) and the bitmask counter (`countSolutions`, stops at 1000); `count.ts` runs it in a module Web Worker (`solver.worker.ts`, main-thread fallback).
     - `SudokuZeroGame.svelte`: 9×9 board (clues in the placer's colour in multiplayer), live counter (`1000+`), clue count and "unique next" bonus, digit pad with row/column/box conflicts disabled (no count preview before committing), tap a digit twice or Place to commit (count is computed, then sent), Give up (two taps) / Pass.

`ActionOutcome.extra_score_deltas` lets a single action credit other players (minesweeper flag challenges); `RoomManager` applies those deltas after the actor's score update.

## Coding Conventions
- Always keep the root `Makefile` up to date so the entire local stack (database, backend, frontend) can be started with `make dev`.
- Use Python 3.12+ syntax (`type` aliases, generics `def foo[T]()`, built-in `dict`, `list`, `tuple`, `X | Y` unions — do not import legacy `typing` equivalents).
- Use `repr(e)` when logging or printing exceptions.
- Use **Psycopg 3** async pools/cursors directly rather than heavy ORMs.
- Landing pages end with a small footer: "by jakob-r" (→ https://www.jakob-r.de/coding/), source code, license (if the repo has one), the legal notice on jakob-r.de and the own privacy page `/privacy` (games.jakob-r.de processes data differently from the static jakob-r.de, so it has its own policy; keep it in sync with data handling and the proxy log setup on the VPS: nginx-proxy `LOG_FORMAT` without `$remote_addr`, size-capped json-file logs). Game sessions (`/{slug}/{roomId}`) have no footer.
- Share image: `og/og.html` is rendered by `make og` (headless Chrome) to `frontend/static/og.png` (1200×630) and set as `og:image`. jakob-r.de/coding uses a copy of it. Re-render when the site changes noticeably.
- App icon / PWA: `og/icon.html` is rendered by `make icons` (headless Chrome + `sips`) to `frontend/static/icons/` (`icon-192/512.png`, `maskable-512.png` with content inside the safe zone, `apple-touch-icon.png`, `favicon-48.png`). `static/manifest.json` names the app "games j" (standalone, cream theme). The root layout always registers `/sw.js` (no fetch handler, so no caching) for installability. Installing is offered only at the bottom of the landing page (`InstallAppPrompt.svelte`): it lazy-loads `@khmyznikov/pwa-install` with `manual-apple`/`manual-chrome`, so the dialog never opens on its own, only via the Install button; hidden in standalone mode. An inline script in `app.html` keeps Chromium's `beforeinstallprompt` (suppressing the browser banner) and hands it to the component.
- **Tests**: backend unit/integration tests with pytest (`make test`). Browser end-to-end tests with **Playwright** in `frontend/e2e/` (`make e2e`, mobile Chromium / Pixel 7, happy paths only). `frontend/playwright.config.ts` starts its own backend on port 8100 with `GAMES_E2E_FIXED=1` and a Vite dev server on 5180, so it runs next to `make dev` against the same Postgres. Fixed mode (`core/e2e.py`, never set in production) makes games deterministic: the host always opens a game started from the lobby (`_order_for_next_game` keeps join order) and 5×5 German Silbenstreit boards are the rows `TISCH BLUME KATZE STERN WOLKE` (`FIXED_BOARD_DE_5`). Each player is a separate browser context with the name preset in `localStorage`, which skips the name prompt. Hubs are prerendered, so tests retry the first click until hydration has happened.

## Production

The root `Dockerfile` builds one image: SvelteKit (`adapter-static`) is compiled into `/app/public`, and uvicorn serves the API, WebSockets, and that SPA on `BACKEND_PORT` (default `8000`). Schema init runs on DB connect (no separate migrate step). `docker-compose.yml` keeps Postgres always available for local `make db`; the `app` service sits behind the Compose `app` profile:

```bash
make docker-up
```

### VPS deployment with Docker Compose

Same pattern as [retromode](https://github.com/jakob-r/retromode): own stack next to an existing [nginx-proxy](https://github.com/nginx-proxy/nginx-proxy) with acme-companion.

- `postgres`: PostgreSQL with a named volume, published only on `127.0.0.1`
- `app`: production image; joins the proxy's Docker network and advertises `VIRTUAL_HOST`, so nginx-proxy routes the hostname (including WebSockets) and Let's Encrypt issues the cert. Until the first cert exists, the app serves ACME challenges from the companion's webroot volume (`ACME_WEBROOT`).

Leave the proxy's Compose file alone and don't edit nginx by hand. DNS for `VIRTUAL_HOST` must already point at the VPS.

1. On the VPS: clone the repo, `cp .env.example .env`, set a strong `POSTGRES_PASSWORD` (Compose overrides `DATABASE_URL` to the internal `postgres` service), then uncomment and fill in `VIRTUAL_HOST`, `LETSENCRYPT_HOST`, `LETSENCRYPT_EMAIL`, `PROXY_NETWORK` (`docker network ls | grep proxy`) and `PROXY_HTML_VOLUME` (`docker volume ls | grep html`).
2. Build and start:

   ```bash
   docker compose --profile app up -d --build
   ```

   Or from the Makefile: `make docker-up`.

3. Check: `docker compose --profile app ps` and `docker compose --profile app logs -f app`. Redeploy with `git pull` plus step 2.

Local image smoke-test (without a real nginx-proxy): create stand-ins once (`docker network create docker_compose_proxy-tier` and `docker volume create docker_compose_html`), then `make docker-up` and hit `http://127.0.0.1:8082`.
